# Property content save repair — 2 October 2026

Status: code, eleven disposable-clone HTTP/SQL groups and all five native cookie/browser groups passed, with completed cleanup. The final-source default suite passes 1,159 tests. Fresh repair install/build/budget/audit also passed on an isolated source snapshot and disposable patched clone. Shared application, staging, production and the complete Property acceptance items remain open.

The organization access rehearsal found that `updateListing` used a signed-in UPDATE against a table whose existing grants deny that write. The repair preserves those revokes and adds `pinpoint_property_save`, a service-role-only, security-invoker database operation. The application derives its actor from `requireAnyPersona`; form-supplied ownership/status claims are discarded by the existing content schema. The database checks the current verified profile/persona and suspension state, locks the listing and any required active organization/manager membership, and checks the form's loaded `updated_at` before changing content.

The operation accepts content fields only. It cannot change listing ID, owner, organization, publication status, place ID, saved homes or image ownership. It retains the existing owner-or-current-active-manager save contract. A stale request raises `PT409`, observed as HTTP 409 through PostgREST; the native action shows an explicit conflict and does not retry or overwrite. The form keeps the returned timestamp after a successful pre-publication save so another attempt does not conflict with its own save. This slice does not repair publication, archive/restore, duplication or the separately failing legacy deletion RPC.

The migration was created with the installed CLI: `supabase/migrations/20261002162631_pinpoint_property_save.sql`. It has been applied only to disposable clones. Shipping source must not be treated as shared-local functionality before its dependency is applied there under a separate runtime correction/checkpoint.
