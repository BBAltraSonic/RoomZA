Simply throwing on those returned errors is insufficient. A retry currently cannot rely on `listing_images` after the listing was deleted: cascading metadata removal loses the cleanup paths. Retain a protected, service-written rollback receipt before a destructive database change becomes durable. It must describe what database work was applied, which exact owned Storage objects still need cleanup, and any resulting listing version needed for the remaining snapshot chain.

Keep the database mutation and its receipt in the same transaction, using service-only invoker RPCs with an empty search path and existing job/organization/version/ownership boundaries. Lock job first, then snapshots/listings in a consistent order. Never grant client writes or trust caller defaults/source flags. New migrations must be created through the CLI and rehearsed only in the clone. Inspect actual snapshot and image-path formats before designing the SQL; preserve partial legacy snapshot fields and existing media rather than blindly replacing missing data with null.

Storage cleanup runs outside PostgreSQL and can fail independently. Check its actual result, retain pending cleanup on failure, and mark a snapshot rolled back only after cleanup and acknowledgement succeed. Retry must recognize already applied database work, safely repeat missing cleanup, and avoid a second delete/restore. Do not return rollback_complete while any operation or cleanup is unresolved. Preserve a truthful partial/failure message and audit trail; capture the actual requesting actor rather than assuming the original job creator performed the rollback.

Handle histories beyond the default1000-row Data API limit, deterministic order, repeated/concurrent requests and snapshot version chains. Derive completion/conflict/pending counts from durable state so a lost response or retry does not double-count. Preserve legitimate owner changes and unrelated images/Storage paths. Additional image-history/version concerns require actual probes before broadening production changes; do not claim a cleanup journal alone proves every media-conflict case.

Required follow-up proof includes successful retry after removing the SQL fault, successful cleanup after restoring Storage, no duplicate database changes or snapshots, preserved owner conflicts and tenant denial, the existing six positive recovery/report cases, larger histories/concurrency/partial reports, and a fresh production browser recovery/download/rollback journey.
