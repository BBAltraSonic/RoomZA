Current primary runtime documentation rules out silently applying a Node-only connection hook as a cross-runtime fix:

- Workers implements node:http through global fetch and does not support request lookup or createConnection options. [Cloudflare HTTP documentation](https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/)
- Workers node:https also wraps global fetch and does not provide direct socket access or the usual TLS configuration controls. [Cloudflare HTTPS documentation](https://developers.cloudflare.com/workers/runtime-apis/nodejs/https/)
- resolveOverride requires both hostnames to be in the same zone, so it does not provide arbitrary external-host IP pinning. [Cloudflare Request documentation](https://developers.cloudflare.com/workers/runtime-apis/request/)
- global_fetch_strictly_public changes own-zone routing; its documentation does not establish that this application pins the checked DNS answer. Its name is not a connection-pinning test, and a compatibility date alone must not be assumed to enable it. [Cloudflare compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/)
- Standalone local Miniflare permits private network targets by default, as observed in installed miniflare/dist/src/index.js. Its successful loopback behavior is not production network-policy proof.
- Current upstream workerd source explicitly treats startTls expectedServerHostname as unsupported, with a gate that can reject it. Connecting to an IP and supplying that option is therefore not a supported generic HTTPS-pinning replacement. This is an upstream source observation, not verification of the deployed runtime version. [Cloudflare workerd source](https://github.com/cloudflare/workerd/blob/main/src/workerd/api/sockets.c%2B%2B#L935)
