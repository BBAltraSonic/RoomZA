# Shopping Offer public reads — 2 October 2026

This additive read layer depends on private permission, place/shop/date review and atomic decisions. The original intake migration, schema and lifecycle remain unchanged. No image is required. These rules govern persisted reads; customer screens and fresh directions redirects are the next dependent slice.

The latest immutable decision must be approval, with no pending revision or withdrawal. The approved revision must still have its exact revision/version permission and location evidence, a matching current catalogue place and a currently eligible poster. Approval references the reviewed content; a later private save does not replace it or hide it. Material submission invalidates approval atomically; rejection cannot restore it. Unpublication and withdrawal remove public eligibility.

The shared private snapshot helper accepts a database clock supplied once per read. An active offer satisfies `startsAt <= now < endsAt`. Feed, paginated map data, count, detail and action destination facts use that helper. Schedules are unnecessary for expiry. Scheduled or expired approved records return only state, stable offer/revision identifiers, area identifier, reviewed dates and confirmation date; their content, place display and poster fields are null. Unknown, never-approved or otherwise unavailable records return only `status: unavailable` and the database clock. No inactive action destination is returned.

Live DTOs expose only approved title, benefit, terms, shop name, public address, exact shop point, validity, selected place display, revision identity and confirmation date. Poster attribution uses the existing public profile username/display name only while its audience is `everyone`; otherwise it is null. Private profile names, user/reviewer UUIDs, authorization references, verification notes, removal reasons and drafts never enter the DTO. DTO validation rejects unknown fields.

Feed requires an app-owned area UUID. It returns twenty entries plus an optional cursor, an exact eligible count and a single server clock. Sorting uses confirmation time and offer UUID, with a complete timestamp/UUID cursor. Map consumers use the same paginated objects and exact shop coordinates. This bound is a transport page size, not a pilot or supply threshold. A stale cursor can produce an empty page as records change; current counts and eligibility are read again.

Public wrappers are deliberately read-only `SECURITY DEFINER` functions with empty search paths and qualified references. This narrowly exposes public DTOs without granting anonymous users private schema usage, private helper execution or base-table access. Default `PUBLIC` execution and service-role execution are revoked; only anonymous and authenticated roles may call these public wrappers. Existing private permissions remain unchanged. The server adapter uses the anonymous key, disables session persistence and fetch caching, and accepts no actor, clock or eligibility flags. This is an intentional anonymous API boundary, rather than an authenticated private operation. See the [Supabase function security guidance](https://supabase.com/docs/guides/database/functions).

The action RPC returns freshly eligible destination facts, not a directions redirect. The next HTTP action handler must recheck remaining validity and use a fixed documented maps destination. A static link from an old page cannot establish continuing eligibility. Open-page expiry, the customer Feed/detail screens, reports/corrections, typed saves, analytics and factual poster activity remain required.

Real permissioned supply and provider provenance are still missing. Synthetic clone records establish behavior only. Shared runtime, fresh migration/RLS acceptance, staging, production and pilot gates remain open. Release 1 remains 2/48 complete.
